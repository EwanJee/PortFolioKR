---
title: Redis master를 놓친 연결
team: retention
summary: "새로 뜬 파드 2개에만 몰린 쓰기 오류를 '클라이언트가 master를 잃은 상태로 고정돼 재시작해야만 회복되는 문제'로 정의하고, 9개 시나리오 로컬 재현으로 원인과 회복 방법(연결을 새로 만들기)을 확인한 뒤, 그 방식으로 연결을 스스로 다시 만드는 자가 복구를 개념 검증(PoC)으로 만들었습니다."
symptom: "약 30분 동안 이벤트 응모 요청이 'Master is currently unknown' 오류와 함께 HTTP 500으로 실패했고(약 100건), 장애 시작 약 5분 뒤 자동 알림이 울렸습니다. 오류는 오토스케일로 새로 뜬 파드 2개에만 몰렸습니다."
definition: "Redis 서버는 정상인데 오류가 특정 파드에만 몰렸으므로, 문제를 서버 장애가 아니라 그 파드의 Redis 클라이언트가 master를 잃은 상태로 고정돼 재시작해야만 회복되는 문제로 정의했습니다. 목표는 파드를 다시 띄우지 않아도 연결이 스스로 회복하게 만드는 것이었습니다."
approach: "로컬 Redis로 장애를 시나리오 9개와 대조군 1개로 재현해 운영 현상과 구조가 같은지 맞춰 봤습니다. 이어서 master가 돌아온 뒤 프로세스 안에서 쓸 수 있는 복구 방법(연결 검사, 연결 공유 끄기, 연결 초기화)과 새 연결 팩토리(연결을 만드는 객체) 생성을 하나씩 시험했습니다."
cause: "Lettuce 6.3.2(자바 Redis 클라이언트)의 master-replica(쓰기는 master 한 대가 맡고 복제본이 읽기를 나누는 구성) 정적 구성에서는 구성을 읽는 순간 master에 닿지 못하면 master가 노드 목록에서 영구히 빠져, master에만 써야 하는 분산 락(서버 여러 대가 같은 작업을 동시에 하지 않게 거는 잠금) 요청이 계속 실패했습니다. 재현 시나리오 9개가 모두 운영에서 본 현상과 구조가 같았고, 락 처리 코드에 예외 처리가 없어 락 실패 응답(409) 대신 500이 나간 것도 확인했습니다."
fix: "오류를 감지하면 연결을 새로 만드는 자가 복구를 개념 검증(PoC)으로 만들었습니다. 여러 요청이 동시에 오류를 봐도 연결은 한 번만 다시 만들고(single-flight), 재시도 간격은 점점 늘립니다(지수 backoff)."
verification: "재현에서 master가 돌아온 뒤에도 프로세스 안 복구 방법은 모두 회복에 실패했고 새 연결 팩토리를 만든 경우만 즉시 회복돼, 연결을 새로 만드는 방식이 맞다는 근거가 됐습니다. 운영에서도 문제 파드 2개를 지운 뒤 오류가 0건이 됐습니다."
prevention: "원인 보고서는 이 오류를 감지하면 파드를 자동으로 교체(준비·생존 확인과 연동, 재현에서 효과 확인)하고, DNS TTL(주소 정보를 캐시에 두는 시간)을 60초에서 5~10초로 줄이자고(효과는 추정) 권고했습니다. 자가 복구는 사람이 파드를 다시 띄우지 않아도 연결이 스스로 돌아오게 하는 것이 목표입니다."
record: "원인 보고서, 증거 문서, 시나리오 9개를 다시 돌릴 수 있는 재현 하네스(재현용 테스트 코드), 다른 가설을 반증한 기록을 남겼습니다. 자가 복구 작업은 Jira 유지보수(KTLO, 운영 유지보수) 작업 1건으로 추적했고, 착수와 목표는 격주 회고에 적었습니다."

order: 2
