---
title: LLM 번역 타임아웃 8.3%
team: global
summary: "번역 타임아웃의 실제 규모를 15일 전수 지표로 다시 재서 8.3%로 확정하고(처음 표본 기준 26~80%), 호출 대상 응답 p99 약 7초와 기본 타임아웃 2초를 대조해 원인을 새 클라이언트의 타임아웃 설정 누락으로 좁혔습니다."
symptom: "LLM 기반 번역 호출이 읽기 타임아웃으로 반복해서 실패했습니다. 번역을 요청한 서버가 오류를 처리해 상위 서비스에 HTTP 오류로 전달되지는 않았지만, 캐시에 없는 항목은 번역되지 않고 원문 그대로 나갔습니다."
definition: "장애가 아니라 오류 표시 없이 번역만 빠지는 품질 문제였으므로, 실제 실패율부터 정확히 재는 문제로 정의했습니다."
approach: "APM(요청 추적 도구)의 스팬(요청 하나를 처리한 기록) 개수로 오류율을 셌더니 26~80%가 나왔지만, 오류 스팬은 모두 남기고 정상 스팬만 일부 남기는 표본 추출 때문임을 알아채고 표본 추출 전 지표로 바꿔 다시 셌습니다. 이어서 호출 대상의 응답 시간 분포, 기존 번역 클라이언트 설정, 다른 번역 경로의 오류율, 코드의 재시도 설정을 차례로 대조했습니다."
cause: "새 번역 클라이언트에 개별 타임아웃이 없어 전역 기본값 2초(연결·읽기)를 물려받았는데, LLM 번역 서버의 응답 시간은 p95 약 3.5초, p99 약 7초(p95·p99는 느린 쪽 5%·1% 경계의 응답 시간), 배치가 도는 날 최대 90~112초라 약 8%는 구조적으로 2초를 넘을 수밖에 없었습니다. 기존 번역 클라이언트는 읽기 타임아웃이 15~20초로 맞춰져 있었고, 새 클라이언트만 이 설정이 빠져 있었습니다."
fix: "즉시 조치로 새 클라이언트의 읽기 타임아웃을 기존 수준인 약 20초로 두고, 근본 조치로 캐시 적중률을 높이고 미리 번역해 두며, LLM 호출 자체에도 마감 시간을 둬 비용 낭비를 막자고 권고했습니다. 재시도는 부하를 키울 수 있어 새로 넣지 말자고 했습니다."
verification: "표본 추출 전 지표로 15일 동안 센 번역 호출 약 280만 건 중 약 23만 건이 타임아웃이어서, 실패율은 8.3%였습니다. 성공한 호출도 p99가 1.91초로 2초에 가까웠고, 다른 번역 경로의 오류율은 약 0%여서 문제가 이 LLM 경로에만 있음을 확인했습니다."
prevention: "새 HTTP 호출 클라이언트를 만들 때 타임아웃 설정이 빠졌는지를 점검 항목으로 남겼습니다. 코드에서 재시도가 꺼져 있음(재시도 안 함 설정)도 확인해, '재시도가 실패를 키웠다'는 잘못된 추정을 배제했습니다."
record: "표본 기준과 전수 기준 수치가 달라진 이유, 원인, 권고를 원인 분석 문서(RCA)로 남겼고, 사내 위키에도 이 건의 원인 분석 페이지가 있습니다. 같은 문서에 호출 쪽 번역 캐시(DB)가 설계 문서의 '상태를 두지 않는다'는 전제와 어긋난다는 설계-코드 불일치도 적었습니다."
evidence: [E-translate]
