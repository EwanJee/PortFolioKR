title: 증설로는 못 막았을 가격 API 장애
team: global
summary: "'증설로 막을 수 있었나'라는 질문을 자원 부족 여부를 가리는 문제로 바꿔, 가격 API를 부르는 프런트 서버에 자원 여유가 있었는데(CPU 3.2% → 3.9%, 메모리 74% → 41%) 들어온 요청 오류만 약 300배 늘었음을 보이고 원인이 느린 하위 API를 동기로 기다린 구조임을 밝혔습니다."
symptom: "세일이 끝난 심야에 가격 조회 API가 타임아웃으로 실패하기 시작해 다른 서비스의 호출 실패와 서킷 브레이커(실패가 이어지면 호출을 잠시 끊는 장치) 열림으로 이어졌고, P1 등급 장애로 자동 보고된 뒤 약 10분 안에 서킷 자동 복구로 해소됐습니다."
definition: "장애 대응 책임자가 '증설 계획은 없었나, 세일 종료는 늘 있던 일인데 왜 이번에만 났나'를 물었고, 이를 '우리 쪽 호출이 원인이었나'와 '자원이 모자랐나' 두 질문으로 나눠 각각 데이터로 답했습니다."
approach: "먼저 장애 구간과, 같은 규모의 대량 가격 변경이 있었지만 장애가 없던 같은 세일의 시작일을 추적 데이터(트레이스)로 나란히 비교했습니다. 이어서 표본 추출(샘플링)을 거치지 않은 자원·오류 지표로 프런트 서버의 장애 구간을 평소와 비교했습니다."
cause: "같은 세일의 시작일에는 우리 배치 서버의 가격 호출(캐시 우회)이 장애 때보다 오히려 많았는데도 장애가 없어(추적 표본 기준), 우리 쪽 설정(캐시 우회, 타임아웃 1초 + 재시도 3회)은 지연을 키운 요인일 뿐이었습니다. 실제 원인은 하위 세일 API가 최근 변경으로 백프레셔(부하 조절)가 풀려 느려지자, 가격 API가 이를 동기로 기다리며 DB 연결을 점유해 다른 API까지 느려진 것이었습니다."
fix: "우선순위 순으로 가격 호출 재시도를 3회에서 0회 또는 1회 + 지터(무작위 대기)로 줄이고, 사내 다른 호출에 이미 쓰던 서킷 브레이커를 가격 호출에도 적용하자고 권고했습니다. 이어서 상품 화면의 고정 캐시 우회를 설정값으로 바꾸되 먼저 캐시 적중률을 재고, 배치 일정이 자정 변경 시간대와 겹치는지 점검하자고 했습니다."
verification: "프런트 서버의 자원 지표는 평소 대비 CPU 3.2% → 3.9%, 메모리 74% → 41%, 메모리 부족 종료·재시작 0건이었고, 배치 서버의 CPU 스로틀(한도 때문에 CPU를 못 쓴 시간)도 평소보다 오히려 적었습니다. 반면 같은 프런트 서버의 비샘플링 오류는 나가는 호출이 약 60배, 들어온 요청이 약 300배로 늘어, 자원이 아니라 느린 호출을 기다린 것이 문제였음을 보여 줬습니다."
prevention: "배치 서버 메모리가 상시 약 95%인 원인, 오토스케일 미설정 가능성, CPU 한도 미설정 가능성을 따로 보는 용량 점검 트랙을 제안했습니다. 'SLA(약속한 응답 수준)를 넘긴 호출이 난 팀이 장애 대응을, 그 API를 제공한 팀이 근본 원인을 맡는다'는 책임 원칙도 합의됐습니다."
record: "장애 티켓 1건으로 관리된 이 장애에 대해 원인 분석 문서(RCA) 2건(가격 API 급증 원인 분석, 증설 여부 후속 분석)을 썼습니다. 문서에는 조치를 우리 팀 몫과 원인 팀 몫으로 나눠 우선순위와 함께 적었습니다."
evidence: [E-price, E-price-research]
order: 4
