title: 증설로는 못 막았을 가격 API 장애
team: global
summary: "'증설로 막을 수 있었나'라는 질문을 '자원이 모자랐나'와 '우리 쪽 호출이 원인인가'로 나누고, 자원 지표와 오류 지표를 평소와 비교해 원인이 느린 하위 API를 동기로 기다린 구조임을 보였습니다."
symptom: "세일이 끝난 심야에 가격 조회 API 호출이 타임아웃으로 실패했고, 그 API를 부르는 우리 팀 서버로 들어온 요청의 오류는 평소의 약 300배로 늘었습니다."
definition: "장애 대응 책임자가 '증설 계획은 없었나, 세일 종료는 늘 있던 일인데 왜 이번에만 났나'를 물었고, 이를 '우리 쪽 호출이 원인이었나'와 '자원이 모자랐나' 두 질문으로 나눠 각각 데이터로 답했습니다."
cause: "대량 변경 규모가 같았던 세일 시작일과 추적 데이터(트레이스)를 비교하니, 그날은 우리 쪽 호출이 더 많았는데도 장애가 없었습니다. 우리 쪽 캐시 우회, 짧은 타임아웃, 재시도는 지연을 키운 요인일 뿐이었고, 실제로는 하위 API가 최근 변경 뒤 느려지자 가격 API가 이를 동기로 기다리며 DB 연결을 붙잡은 것이 원인이었습니다."
fix: "표본 추출이 없는 자원 지표를 다시 보니 CPU는 평소 수준, 메모리는 오히려 평소보다 낮았고 메모리 부족 종료나 재시작도 없었는데 오류만 폭증해, 증설로는 막지 못했을 장애라고 결론 냈습니다. 그래서 재시도를 줄이고, 사내에서 이미 쓰던 서킷 브레이커(실패가 이어지면 호출을 잠시 끊는 장치)를 가격 호출에도 적용하자고 우선순위와 함께 권고했습니다."
prevention: "용량 점검은 별도 작업으로 나누자고 제안했고, 약속한 응답 시간을 넘긴 호출은 호출한 팀이 장애 대응을, API를 제공한 팀이 근본 원인을 맡는다는 책임 원칙이 합의됐습니다."
evidence: [E-price]
order: 4
